# Markdown HTML Preview

Converts an existing markdown file (or a set of them) into a matching, self-contained
HTML file for easier viewing — e.g. the plan, design, scaffolding, implementation, or
verification docs produced by the feature workflow, or any other markdown file in the
repo. The HTML is authored directly by hand rather than generated by a conversion
script, so it can actually be shaped around the document's content — a design doc's
endpoint tables and a report's deviation list don't have to look identical just
because they're both markdown. Purely a rendering convenience: never changes the
meaning of the content, and never runs unless the user actually asks for HTML.

## When this applies

- Explicit requests for an HTML version of a markdown doc: "give me an HTML version
  of X", "convert Y.md to HTML", "make the design doc viewable as HTML"
- Requests covering several docs at once: "give me HTML versions of all the docs for
  this feature"

**Does not apply otherwise.** Don't generate an HTML twin as an automatic side effect
of creating or editing a markdown file in any other skill — only do this work when
asked for it directly, in this request or a standing instruction from the user.

## Workflow

### Step 1: Identify the markdown file(s)

If the user names a path directly, use it. If they refer to a doc more loosely (e.g.
"the design doc for CSV export," "all the docs for this feature"), locate it the same
way the rest of the feature workflow does — check `/plans`, `/designs`, `/reports`,
`/verification`, and their `/docs/...` equivalents for a matching feature slug. If
nothing matches and the file can't be found, say so and ask rather than guessing at a
path.

### Step 2: Read the whole document before writing anything

Read the complete markdown file first. Note its actual shape — which sections are
prose, which are field tables, which are lists, whether there's a request/response
pair per endpoint, a deviation-per-entry structure, etc. This is what direct
authoring buys over a generic converter: the HTML structure can match what the
content actually is, not just whatever a one-size-fits-all parser produces.

### Step 3: Write the HTML by hand

Write real, semantic HTML directly to a file using your environment's file-writing
tool — no markdown library, no
conversion script. Translate each element deliberately:

- Headings → `<h1>`/`<h2>`/`<h3>` matching the source's heading levels
- Bullet/numbered lists → real `<ul>`/`<ol>`/`<li>`, correctly nested by hand (this
  sidesteps the lazy-list and indentation quirks a markdown parser can introduce —
  there's no parser to trip over)
- Tables → real `<table>`/`<thead>`/`<tbody>` markup
- Bold/italic/inline code/links → `<strong>`/`<em>`/`<code>`/`<a>`
- Fenced code blocks → `<pre><code>`, preserving the code exactly as written,
  including whitespace
- Prose paragraphs → plain `<p>` tags, not reformatted into lists or tables that
  weren't there in the source

Where it genuinely helps readability, use judgment to give recurring structures a
tailored treatment consistent with what the content actually is — for example, an
API endpoint's method + path as a small styled label instead of plain text, a
name/type/notes field list as a real table even if the source wrote it as bullets, a
"Deviations" or "Open questions" section set off as a distinct callout block. This is
a formatting choice, not a content change — the words and facts must stay exactly
what the source says. Don't invent structure that isn't implied by the content, and
don't apply a heavy template that fights the document's actual shape.

Wrap the content in a minimal HTML shell with a small embedded `<style>` block:
system font stack, a comfortable max-width, and styles for whatever elements the
document actually uses (headings, lists, tables, code, blockquotes, callouts, links,
rules). No external stylesheets, fonts, or scripts — the file should open and look
right on its own, with nothing to fetch.

### Step 4: Verify fidelity before finishing

Direct authoring trades a mechanical converter's guaranteed fidelity for the
flexibility to format well — that flexibility only pays off if the content is still
accurate. Before considering the file done, go back through the source markdown
section by section and confirm every fact, list item, table row, code block, and
sentence made it into the HTML unchanged in meaning. Catch anything paraphrased,
dropped, reordered in a way that changes meaning, or added that wasn't in the
source, and fix it.

### Step 5: Save alongside the original

Save as the same filename with a `.html` extension, in the same folder as the source
markdown (e.g. `plans/csv-export.md` → `plans/csv-export.html`). If a file with that
name already exists, overwrite it — this is a regenerated view of the current
markdown, not a versioned artifact.

### Step 6: Multiple docs

If the request covers several docs (e.g. "the whole feature"), write each one
individually, one HTML file per markdown file, following Steps 2–5 for each. Docs of
different types (a plan vs. a report, say) can end up looking different from each
other since each is authored around its own content — that's expected, not a
consistency bug. Don't build a combined index or navigation page unless the user
specifically asks for one.

## Guardrails

- Never trigger without an explicit request for HTML
- Never alter, summarize, reword, or reorganize the *content* during authoring —
  formatting choices (tables, callouts, labels) are fine; changing what something
  says is not
- Keep the HTML self-contained — no CDN links, no external CSS/JS/fonts
- If the referenced markdown file doesn't exist, say so rather than generating HTML
  from assumed or fabricated content
- Always run the Step 4 fidelity check — hand-authored HTML has no automatic
  guarantee it matches the source the way a converter's output would, so that check
  isn't optional busywork, it's the thing that makes direct authoring safe to use
